# ADR-002: Выбор PostgreSQL как базы данных

**Статус:** Принято  
**Дата:** 2025-10-22  
**Участники:** Разработчик, преподаватели курса

## 1. Контекст и проблема

"Какую базу данных использовать для хранения записей о просмотрах фильмов (diary entries) и информации о фильмах в приложении Vulpecula, чтобы обеспечить производительность (время отклика <= 500 мс), надежность хранения данных, удобство разработки и возможность интеграционного тестирования?"

## 2. Архитектурно значимые требования (ASR)

| ID требования | Текст требования | Тип | Источник |
|---------------|------------------|-----|----------|
| PERF-001 | Время отклика API <= 500 мс для запросов к базе данных | НФТ | Техническое задание |
| PERF-002 | Оптимизация запросов для быстрого получения данных о просмотрах | НФТ | Техническое задание |
| SCAL-002 | Поддержка роста данных до 1000+ записей на пользователя | НФТ | Функциональные требования |
| DEV-001 | Простая локальная разработка и запуск в Docker/Testcontainers | НФТ | Учебный проект |
| COST-001 | Минимизация затрат для учебного проекта | НФТ | Бюджетные ограничения |
| REL-001 | Надежность хранения данных, отсутствие потерь | НФТ | Техническое задание |

## 3. Анализ альтернатив

| Требование \ Решение | PostgreSQL | MongoDB | DynamoDB |
|---------------------|------------|---------|----------|
| PERF-001 | Подходит при использовании индексов и ограниченных выборок | Подходит для документных запросов | Подходит для заранее известных access patterns |
| PERF-002 | SQL, индексы, транзакции, планировщик запросов | Aggregation pipeline и индексы | Partition key, sort key, GSI |
| SCAL-002 | Достаточно для текущего масштаба проекта | Достаточно для текущего масштаба проекта | Высокая масштабируемость |
| DEV-001 | Простая локальная среда через Docker Compose и Testcontainers | Требуется отдельный сервис | Требуется AWS/localstack или мок-окружение |
| COST-001 | Бесплатно локально, дешево в учебном окружении | Бесплатно локально, платно в Atlas | Free tier, но сложнее локальная инфраструктура |
| REL-001 | ACID-транзакции и зрелые механизмы backup | Документная модель, транзакции ограниченнее | Надежный managed-сервис |
| Сложность схемы | Реляционная модель хорошо подходит для записей просмотров | Гибкая документная модель | Требует проектирования access patterns заранее |
| Интеграция с приложением | Есть драйвер JDBC, Exposed, миграции Liquibase | Требуется отдельная реализация | Требуется AWS SDK и отдельная модель доступа |

## 4. Выбранное решение

**PostgreSQL** с:

* отдельным подпроектом `entry-repo-pgjvm`;
* доступом к данным через JDBC и Exposed;
* схемой таблиц, управляемой миграциями Liquibase;
* локальным запуском через Docker Compose;
* интеграционными тестами через Testcontainers.

Основная таблица записей просмотров хранит идентификатор записи, пользователя, фильм, дату просмотра, оценку, комментарий и lock для оптимистичной блокировки.

## 5. Обоснование

Решение удовлетворяет критическим требованиям проекта:

* **PERF-001**: PostgreSQL укладывается в требуемое время ответа <= 500 мс для текущего масштаба проекта при корректных индексах и ограниченных выборках.
* **PERF-002**: SQL и индексы позволяют эффективно реализовать чтение, поиск по фильму, поиск по комментарию и фильтрацию по датам.
* **SCAL-002**: Для учебного проекта и ожидаемого объема данных PostgreSQL обеспечивает достаточный запас производительности.
* **DEV-001**: PostgreSQL легко запускать локально и в CI через Docker Compose/Testcontainers, что упрощает проверку репозитория.
* **COST-001**: Для разработки и тестирования база запускается локально без дополнительных затрат.
* **REL-001**: ACID-транзакции, ограничения схемы и зрелые механизмы резервного копирования снижают риск потери или неконсистентности данных.

Дополнительные преимущества:

* простая проверка SQL-схемы через миграции;
* понятная модель данных для записей просмотров;
* хорошая совместимость с Kotlin/JVM, Ktor и Exposed;
* возможность использовать один и тот же репозиторный контракт для InMemory и PostgreSQL-реализаций.

## 6. Последствия

**Позитивные:**

* реализация соответствует текущему коду проекта;
* проще проводить интеграционные тесты репозитория;
* можно использовать транзакции и оптимистичную блокировку;
* ниже сложность разработки по сравнению с DynamoDB для текущей модели данных;
* проще анализировать и отлаживать запросы.

**Негативные:**

* горизонтальное масштабирование сложнее, чем у managed NoSQL-решений;
* для production потребуется настроить backup, мониторинг и параметры подключения;
* при росте нагрузки потребуется следить за индексами и планами запросов.

**Зависимости:**

* Docker Compose/Testcontainers для интеграционного тестирования;
* Liquibase для миграций схемы;
* JDBC-драйвер PostgreSQL и Exposed для доступа к данным.

| PERF-002 | Тестирование поиска и фильтрации | Поиск по movieId, комментарию и датам возвращает корректные данные | Реализовано в контрактных тестах |

| DEV-001 | Запуск тестов репозитория через Testcontainers | PostgreSQL поднимается автоматически для тестов | Реализовано |

| REL-001 | Проверка create/read/update/delete и optimistic locking | Данные сохраняются корректно, конфликт lock обрабатывается | Реализовано в контрактных тестах |
