# ADR-002: Choosing PostgreSQL as Database

**Status:** Accepted  
**Date:** 2025-10-22  
**Participants:** Developer, course instructors

## 1. Context and Problem

"Which database should be used for storing movie viewing entries (diary entries) and movie information in the Vulpecula application to ensure performance (response time <= 500 ms), reliable data storage, convenient development, and integration testing?"

## 2. Architecturally Significant Requirements (ASR)

| Requirement ID | Requirement Text | Type | Source |
|----------------|------------------|------|--------|
| PERF-001 | API response time <= 500 ms for database queries | NFR | Technical specification |
| PERF-002 | Query optimization for fast retrieval of viewing data | NFR | Technical specification |
| SCAL-002 | Support for data growth up to 1000+ entries per user | NFR | Functional requirements |
| DEV-001 | Simple local development and execution with Docker/Testcontainers | NFR | Educational project |
| COST-001 | Minimizing costs for educational project | NFR | Budget constraints |
| REL-001 | Data storage reliability, no data loss | NFR | Technical specification |

## 3. Analysis of Alternatives

| Requirement \ Solution | PostgreSQL | MongoDB | DynamoDB |
|------------------------|------------|---------|----------|
| PERF-001 | Suitable with indexes and bounded queries | Suitable for document queries | Suitable for predefined access patterns |
| PERF-002 | SQL, indexes, transactions, query planner | Aggregation pipeline and indexes | Partition key, sort key, GSI |
| SCAL-002 | Sufficient for the current project scale | Sufficient for the current project scale | High scalability |
| DEV-001 | Simple local environment with Docker Compose and Testcontainers | Requires a separate service | Requires AWS/localstack or mock environment |
| COST-001 | Free locally, inexpensive in an educational environment | Free locally, paid in Atlas | Free tier, but more complex local infrastructure |
| REL-001 | ACID transactions and mature backup mechanisms | Document model, more limited transactions | Reliable managed service |
| Schema complexity | Relational model fits viewing entries well | Flexible document model | Requires access pattern design upfront |
| Application integration | JDBC driver, Exposed, Liquibase migrations are available | Requires a separate implementation | Requires AWS SDK and a separate access model |

## 4. Selected Solution

**PostgreSQL** with:

* a dedicated `entry-repo-pgjvm` subproject;
* data access through JDBC and Exposed;
* schema management with Liquibase migrations;
* local execution through Docker Compose;
* integration tests through Testcontainers.

The main viewing entry table stores the entry id, user id, movie id, viewing date, rating, comment, and lock for optimistic locking.

## 5. Rationale

The solution satisfies the critical project requirements:

* **PERF-001**: PostgreSQL can meet the required response time <= 500 ms for the current project scale with proper indexes and bounded queries.
* **PERF-002**: SQL and indexes support efficient read operations, search by movie, search by comment, and date filtering.
* **SCAL-002**: PostgreSQL provides enough performance headroom for the expected educational project data volume.
* **DEV-001**: PostgreSQL is easy to run locally and in CI through Docker Compose/Testcontainers, which simplifies repository verification.
* **COST-001**: Development and testing can run locally without additional paid services.
* **REL-001**: ACID transactions, schema constraints, and mature backup mechanisms reduce the risk of data loss or inconsistency.

Additional advantages:

* schema verification through migrations;
* a clear data model for viewing entries;
* good compatibility with Kotlin/JVM, Ktor, and Exposed;
* the same repository contract can be used for InMemory and PostgreSQL implementations.

## 6. Consequences

**Positive:**

* implementation matches the current project code;
* repository integration testing is straightforward;
* transactions and optimistic locking are available;
* lower development complexity than DynamoDB for the current data model;
* queries are easier to analyze and debug.

**Negative:**

* horizontal scaling is more complex than with managed NoSQL solutions;
* production deployment requires backup, monitoring, and connection settings;
* indexes and query plans must be monitored as load grows.

**Dependencies:**

* Docker Compose/Testcontainers for integration testing;
* Liquibase for schema migrations;
* PostgreSQL JDBC driver and Exposed for data access.
